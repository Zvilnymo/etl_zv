# Реєстр і кодифікація документів клієнтів (Google Диск → поля CRM)

## Що це

Файли в папках «Клієнти» та «Клієнти_клон» на Google Диску (600k+) розкладаються
за сегментами — **блоками справи** з каталогу полів CRM (`crm_fields_catalog.xlsx`, 26 блоків).
Кожен файл отримує код, а кожен тип документа звʼязаний з конкретними полями CRM,
які з нього має заповнити парсер.

| Код | Що означає | Приклад |
|---|---|---|
| `ZV-BB` | Блок справи (сегмент) | `ZV-14`: Кредитори та борг |
| `ZV-BB.TT` | Тип документа в блоці | `ZV-14.02`: Кредитний звіт УБКІ |
| `ZV-F-BB.NNN` | Поле CRM (блок поля + № у блоці), код постійний | `ZV-F-14.012` → `UF_CRM_…` |
| `ZV-BB.TT-КЛІЄНТ-NNNN` | Екземпляр документа | `ZV-14.02-K3F9A0B12C4D-0002`: другий звіт УБКІ клієнта |

`КЛІЄНТ` — стабільний ключ папки клієнта (`K` + 11 hex від ID папки). Файли, що лежать прямо в корені,
отримують ключ `R…`. Телефон з назви папки (`ПІБ, +380…`) зберігається окремо: за ним реєстр
стикується з контактом Bitrix24.

Блок `00` — службові файли: `00.01` скан без типу (потрібен OCR), `00.02` архіви / lock-файли,
`00.03` медіа, `00.04` робочі нотатки юриста, `00.05` звіти перевірки КЕП, `00.00` не розпізнано.

## Як класифікується файл

1. **Назва файлу**: регулярки типу документа, напр. `убкі|ubki|кредитн.* істор` → `14.02`.
2. **Назви папок**: найближча папка важить найбільше, напр. «УБКІ» → `14.02`, «Заява АК» → `18.x`,
   «Декларації» → `17.07`. Папка підтверджує тип із назви або сама визначає тип, коли назва
   неінформативна (`04.02.pdf`, `2024.docx`).
3. «Особисті документи» не задають тип, а лише звужують коло блоків (01–12).
4. Коли в назві є лише кредитор (`Мілоан 01.05.2025.pdf`), тип визначає папка, а без неї ставиться `14.07`.
5. Документи родичів (`паспорт + іпн матір`, `дохід сестра`) переносяться в `02.04` / `05.05`.
6. Якщо нічого не спрацювало, тип визначається за mimeType (`00.xx`) з впевненістю 0.2.

Додаткові ознаки в реєстрі: `creditor` (з довідника кредиторів), `subject` (боржник / родич),
`is_archived` (папки «старе», «не актуально»), `not_for_court` («Не в суд»), `needs_check` («ПЕРЕВІРИТИ_»),
`is_copy`, `is_duplicate` (той самий md5 у клієнта), `signed_container` (`.p7s` / `.asice`),
`also_contains` (комбіновані скани на кшталт «паспорт + іпн»), `sensitive` (ЕЦП, паролі: вміст не читати).
Файли з паролями, логінами, ключами (`пароль`, `password`, `логін`, `.jks`, `.pfx`, `Key-6.dat`, папки «ЕЦП», «Паролі», «Доступи»)
позначаються `sensitive` і `parse = skip`, який би тип документа не переміг. Ручне виправлення типу цю позначку не знімає.
Слова з назви папки клієнта (ПІБ) не враховуються при визначенні родича та кредитора, тож прізвища
на кшталт «Братко» чи «Алексеєнко» не дають хибних збігів.

Ручне виправлення: рядок у `docs.doc_type_overrides (file_id, doc_type)` переважає правила при наступному запуску.

## Запуск

Сервісному акаунту (той самий JSON, що для Google Sheets, або окремий `GOOGLE_DRIVE_CREDENTIALS`)
треба дати доступ **«Переглядач»** на «Клієнти» та «Клієнти_клон». Якщо це Google Workspace,
можна натомість увімкнути domain-wide delegation і задати `GOOGLE_DRIVE_SUBJECT=info@zvilnymo.com.ua`.

```bash
psql "$DATABASE_URL" -f db/migrations/023_add_doc_registry.sql

# пілот без БД: 20 клієнтів з кожного кореня → Excel
python -m etl.gdrive.doc_registry_etl --no-db --limit-clients 20 --xlsx /tmp/pilot.xlsx   # поза репозиторієм: там ПІБ і телефони

# повний реєстр у PostgreSQL (≈ 600k файлів; 8 потоків, GDRIVE_WORKERS)
python main.py --mode doc-registry
# щоденний інкремент (файли, змінені після останнього завантаження)
python main.py --mode doc-registry-incremental
```

Коди полів постійні: карта `crm_code → field_code` лежить у `etl/gdrive/field_codes.json`.
Нове поле в каталозі отримує наступний вільний номер у своєму блоці, а наявні коди не перенумеровуються.
Коди документів теж ніколи не перевикористовуються. Лічильник `docs.doc_seq_counters` не зменшується,
тому номер видаленого чи перекласифікованого документа не дістанеться іншому файлу.

Інкремент бере файли з `modifiedTime` або `createdTime` після початку останнього успішного запуску
(`docs.etl_state`). Мітка зсувається лише після запуску без помилок. Переміщення файлів між папками
клієнтів і видалення інкремент не бачить, тому повний запуск треба робити регулярно, напр. раз на тиждень.
Після зміни правил у `taxonomy.py` також потрібен повний запуск.

Повний запуск також видаляє з реєстру файли, яких більше немає на Диску. Робить це лише тоді,
коли обхід пройшов без помилок. Перед обходом кожен корінь перевіряється через API: без доступу запуск
одразу завершується помилкою. Корінь, що не дав жодного файлу, рахується як помилка, тож його рядки не видаляються.
Ярлики на папки обходяться, ярлики на файли пропускаються, бо сам файл лежить у своїй папці.
Папка, що не прочиталась, повторюється один раз через 30 с.

У `crm.etl_runs` частковий запуск (`partial`) пишеться як `error` з поясненням.

## Для парсера

```sql
-- що парсити і які поля CRM заповнити з кожного документа
SELECT doc_instance_code, doc_code, parse, file_id, crm_fields
FROM docs.vw_parse_queue
WHERE doc_code = 'ZV-14.02' AND confidence >= 0.8;

-- зведення по сегментах
SELECT * FROM docs.vw_registry_segments ORDER BY doc_code;
```

`parse`: `ocr` (скан / фото), `text` (docx / gdoc), `table` (xlsx / gsheet), `unzip` (архів, тип визначено за назвою,
парсити після розпакування), `skip` (не парсити).
Черга не включає чутливі, архівні файли та дублі. Серед копій одного файлу (однаковий md5) оригіналом
вважається неархівна копія з конкретним типом. Output-звʼязки (поля, які йдуть у Заяву, План, Декларацію) не є ціллю
парсингу: це наші чернетки, тож у черзі їх немає. `subject = relative`: дані родича, а не боржника.
`creditor` вказує, до якого елемента СП «Список кредиторів клієнта» писати.

## Пілот (6 клієнтів, 1451 реальний файл, жовтень 2026)

| Впевненість | Файлів | Частка |
|---|---|---|
| ≥ 0.8: назва + папка | 778 | 54 % |
| 0.5–0.79: переважно тільки папка | 642 | 44 % |
| < 0.5: не розпізнано (`00.00` / `00.01`) | 31 | 2 % |

Нерозпізнані файли — це скани, названі ініціалами родичів («<Прізвище> В. А..pdf»), «Витяг.pdf», «р .pdf»,
«Новый документ».

## Обмеження

* Класифікація йде за назвами файлів і папок, вміст не читається. Файли `00.01` / `00.00`
  (фото з телефона, `scan.pdf`) потребують другого проходу: OCR перших сторінок і ті самі регулярки
  по тексту.
* Звʼязки `evidence` беруть лише поля з роллю «Доказ: реквізити / відомості з документа». Слоти
  «Кредитор N», агрегати по клієнту, архівні, технічні та судові поля відкинуто. Поля, які каталог
  не класифікував, але які напряму заповнюються з документа (номер і дата кредитного договору, ЄДРПОУ кредитора,
  дані з відповіді кредитора), підвʼязано явно (`EXTRA_FIELDS` у `taxonomy.py`, звʼязок `extra`).
  Назву та посилання на файл-джерело парсер записує в `PROVENANCE_FIELDS`.
* `subject = relative`: документ родича. Його дані не можна писати в поля самого боржника, і
  `vw_parse_queue` віддає цю ознаку парсеру.
* Блоки 03, 04, 06 (соцстатус, зайнятість, витрати) та частина типів блоків 02, 07, 08 не мають полів у CRM
  (аркуш «Прогалини CRM» у кодифікаторі). Документи реєструються, але парсити їх поки нікуди.
